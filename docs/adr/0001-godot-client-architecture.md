# ADR 0001: Архитектура клиента на Godot

## Status

ЧЕРНОВИК.
Решение действует для текущего клиента MOBA2 на Godot 4.7.

## Context

Сейчас разрабатывается только клиент в `client/`. Проект должен оставаться
запускаемым и поддерживать раздельные игровые данные, представление и UI.
Godot строит приложение вокруг узлов и сцен, а сцены подходят для композиции
объектов, принадлежащих игровому дереву. При этом не все игровые правила
должны зависеть от дерева сцены или от API движка.

Нужно выбрать простую основу, которая не закрывает путь к авторитетному
серверу, но и не создаёт заранее сервер, протокол или транспорт. Сервер в
будущем будет находиться вне `client/` и владеть соревновательным состоянием.

## Decision

- Клиент строится как scene-oriented Godot client: небольшие сцены по
  игровым областям, композиция вместо глубокой иерархии наследования.
- Полный ECS первоначально не вводится. Состояние, представление и UI
  разделяются обычными узлами, ресурсами и небольшими специализированными
  классами. Например, сцена героя владеет визуальными дочерними узлами, но не
  обязана владеть правилами матча.
- Типизированный `Resource` используется только для неизменяемой или
  авторски созданной конфигурации и игровых данных, например параметров
  способности из `.tres`.
- Runtime-состояние, которому нужна ссылочная семантика, хранится в
  типизированных `RefCounted` классах. Оно не становится `Node` только ради
  удобства хранения.
- `Node-free` относится только к правилам, которые не зависят от API Godot.
  Правила, использующие физику, ввод, дерево сцены или другие API движка,
  могут оставаться Godot-зависимыми.
- Между клиентской логикой и конкретным транспортом находится протокольный
  адаптер. Клиент работает с сообщениями и снимками через этот слой, не
  зная деталей транспорта.
- Базовая синхронизация представления использует snapshots и interpolation.
  Ограниченное локальное предсказание движения можно добавить позже, если
  измеренные задержка и отзывчивость этого потребуют.
- Авторитетный сервер остаётся вне `client/`. Это решение не задаёт его
  runtime, протокол, частоту тиков или транспорт.

## Boundaries

- Клиент не считается источником истины для соревновательных правил.
- В решение не входит реализация сервера, сетевого транспорта или протокола.
- Не обещается общий код между клиентом и будущим сервером. Общий код
  возможен только после отдельной проверки требований и стоимости поддержки.
- Не обещается детерминизм физики Godot между разными runtime. Локальная
  физика нужна для представления и отклика клиента, а не как контракт
  воспроизводимости серверного состояния.
- Не следует превращать каждый объект в `Node`, если ему не нужны жизненный
  цикл, сигналы, дерево сцены или API Godot.
- Не следует превращать каждое значение в `Resource`: `Resource` здесь не
  является универсальным контейнером runtime-состояния.

## Consequences

Положительные последствия:

- Новому разработчику проще найти поведение: сцены отвечают за композицию,
  `Resource` за авторские данные, `RefCounted` за runtime-состояние, а
  адаптер за границу транспорта.
- Клиент можно развивать без преждевременного ECS и без фиксации будущего
  серверного устройства.
- Снимки и интерполяция дают безопасную базу для сетевого представления, не
  делая локальное предсказание обязательным.

Цена решения:

- При росте количества сущностей или систем композиция на узлах может стать
  узким местом. Тогда потребуется измеримый план миграции, а не общий ярлык
  «ввести ECS».
- Слой адаптера добавляет границу и типы сообщений, которые нужно поддерживать.
- Без общего кода часть моделей или проверок может быть реализована отдельно
  для клиента и сервера.
- Интерполяция добавляет задержку отображения. Предсказание движения, если
  оно появится, потребует отдельной обработки исправлений от сервера.

## Rejected alternatives

### Полный ECS с первого дня

Отклонено. В текущем клиенте нет подтверждённой потребности платить за
дополнительную архитектурную сложность и миграционные правила ECS. Вернуться
к этому варианту можно по измерениям, а не по моде.

### Всё хранить в `Node`

Отклонено. Узлы полезны для сцены и жизненного цикла Godot, но runtime-данные
и правила без зависимости от движка не должны искусственно зависеть от дерева.

### Всё хранить в `Resource`

Отклонено. `Resource` хорошо подходит для сериализуемых авторских данных, но
не должен становиться универсальным типом для изменяемого runtime-состояния.

### Общий код клиента и сервера заранее

Отклонено. Сервер ещё не спроектирован, а его runtime и требования к
воспроизводимости неизвестны. ADR не делает обещаний о cross-runtime shared
code.

### Локальное предсказание как обязательная основа

Отклонено. Сначала используется snapshots/interpolation. Предсказание движения
добавляется только для конкретной измеренной проблемы отзывчивости.

### Делать физику Godot детерминированным контрактом сервера

Отклонено. ADR не утверждает full determinism и не использует физику Godot как
гарантию одинакового результата между runtime.

## Reconsideration triggers

Решение нужно пересмотреть, если появится хотя бы одно из условий:

- профилирование покажет, что композиция сцен и узлов не выдерживает нужного
  числа объектов или систем;
- повторяющиеся операции над большими наборами сущностей потребуют другой
  модели хранения и обхода;
- snapshots/interpolation не обеспечат принятую отзывчивость или качество
  отображения при измеренной сетевой задержке;
- серверный контракт потребует строго заданной модели сообщений или
  воспроизводимости, которую текущий адаптер не может выразить;
- появится подтверждённая потребность в общем коде и будет выбран способ
  сборки и тестирования для обоих runtime;
- Godot изменит ограничения или возможности, на которых основана эта схема.

При пересмотре сначала фиксируются измерения, граница проблемы и стоимость
миграции. Решение об ECS, предсказании или общем коде принимается отдельно.

- [`../../AGENTS.md`](../../AGENTS.md), разделы «Current scope», «Project
  organization» и «Architecture rules»: активен клиент в `client/`, будущий
  авторитетный сервер находится вне него, рекомендуются композиционные сцены,

  проект MOBA2 запускается со сцены `res://scenes/bootstrap/main.tscn` и
  использует Godot 4.7.
- [Nodes and scenes, Godot 4.7](https://docs.godotengine.org/en/4.7/getting_started/step_by_step/nodes_and_scenes.html):
  официальная модель узлов и сцен, на которой основана scene-oriented часть
  решения.
- [Resource, Godot 4.7](https://docs.godotengine.org/en/4.7/classes/class_resource.html):
  официальное описание базового типа ресурсов, используемого для
  авторских и сериализуемых данных.
- [RefCounted, Godot 4.7](https://docs.godotengine.org/en/4.7/classes/class_refcounted.html):
  официальное описание ссылочного базового класса для runtime-объектов без
  узла сцены.
- [Physics interpolation, Godot 4.7](https://docs.godotengine.org/en/4.7/tutorials/physics/interpolation/physics_interpolation_introduction.html):
  официальное объяснение интерполяции физического представления, на котором
  основан выбор snapshots/interpolation как базового направления.
- [High-level multiplayer, Godot 4.7](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html):
  рекомендация не доверять клиенту соревновательные решения и различие между
  высокоуровневым и низкоуровневым сетевыми API.
- [Physics introduction, Godot 4.7](https://docs.godotengine.org/en/4.7/tutorials/physics/physics_introduction.html):
  ограничения воспроизводимости встроенной физики Godot между разными runtime.
